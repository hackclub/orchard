Scale an app out with more replicas so that it handles more traffic and survives a pod restart, or scale it up with more CPU and memory. Health checks tell Orchard when a pod is ready, so a deploy only sends traffic to pods that work. You can also stop an app to free its resources and start it again later.

## Change replicas

<Tabs syncKey="dashPlusCli">
<TabItem label="Dashboard">

1. Open the app.
2. Go to **Overview**.
3. In **Pods**, use the **Replicas** control to set the count.

</TabItem>
<TabItem label="CLI">

```sh
orchard deploy scale <id> 3
```

</TabItem>
</Tabs>

A deploy does not drop traffic if more than one replica is up and health checks pass.

## Stop and start an app

Stopping an app scales it to zero and keeps its replica count for later. While the app is stopped, Orchard holds pushes to its repository and does not build them. The header shows how many pushes it holds, such as **3 pushes since**.

<Tabs syncKey="dashPlusCli">
<TabItem label="Dashboard">

To stop the app, open **More actions** in the header and select **Stop**.

To start it again, take one of these steps in the header:

- Select **Start**.
- If pushes are held, select **Build and start**. Orchard builds the newest held commit.
- To build from the current branch head, open **More actions** and select **Deploy and start**.

**Restart** stays off until the app runs.

</TabItem>
<TabItem label="CLI">

```sh
orchard deploy stop <id>
orchard deploy start <id>
orchard deploy start <id> --build
```

`start` builds the newest held push if one exists. `--build` rebuilds from source before starting.

</TabItem>
</Tabs>

## Set CPU and memory

<Tabs syncKey="dashPlusCli">
<TabItem label="Dashboard">

1. Open the app.
2. Go to **Settings** > **Resources**.
3. In **CPU and memory**, select the sizes.
4. Select **Save**. Saving restarts the app.

</TabItem>
<TabItem label="CLI">

```sh
orchard deploy resources set <id> --cpu 500 --memory 512Mi
```

`--cpu` is in millicores. A value of `0` clears the setting to the organization default.

</TabItem>
</Tabs>

The value you select is the container's limit. If a superadmin has [turned resource limits off](/operate/resource-limits/), the resource picker shows that limits are off and these sizes do not apply. To size an app from its measured usage, [apply resource suggestions](/deploy/resource-suggestions/).

- **Memory:** The request equals the limit. The app gets that amount, and Kubernetes kills it if it uses more.
- **CPU:** The request is 10% of the limit, with a minimum of 50 millicores. The app can use CPU up to the limit when the node has capacity. To change this, set `CPU_REQUEST_RATIO` and `CPU_REQUEST_MIN_MILLI` on the server.

:::caution
When you change resources through the API, send every field you want to keep. An omitted value falls back to the organization default, which may be smaller than the current size.
:::

## Attach a GPU or other device

An app can use a host device, such as a GPU for transcoding or inference, when your instance offers one. Only the devices that a superadmin [makes available](/operate/devices/) appear. If none do, the **Devices** section is hidden.

<Tabs syncKey="dashPlusCli">
<TabItem label="Dashboard">

1. Open the app.
2. Go to **Settings** > **Resources**.
3. In **Devices**, turn on the device, or select how many to attach.

</TabItem>
<TabItem label="CLI">

```sh
orchard deploy devices set <id> --device nvidia.com/gpu=1
```

Pass `--device` once for each device. A device you leave out is detached, and `--none` detaches all of them.

</TabItem>
</Tabs>

The app restarts to pick up the change. Each pod gets its own device, so a pod that cannot get one stays in **Pending** until a device is free. With one GPU, run one replica.

An app with a device always uses the **Recreate** [update strategy](/deploy/update-strategies/), so that the old pod releases the device before the new one starts. Attaching a device switches the app to Recreate, and rolling and blue-green updates are unavailable until you detach it.

## Set health checks

Health checks decide whether a pod counts as ready. An app that runs but fails its check shows as failing. Orchard applies the checks again on each rebuild.

<Tabs syncKey="dashPlusCli">
<TabItem label="Dashboard">

1. Open the app.
2. Go to **Settings** > **Health checks**.
3. Turn on **Check this app**.
4. In **Check with**, select the method.
5. Enter the path or command, and the port.
6. Select what the check controls: **Restart the container when it fails**, **Stop sending traffic until it passes**, or **Allow extra time on startup**.
7. Select **Save**. Saving restarts the app.

</TabItem>
<TabItem label="CLI">

```sh
orchard deploy health-check set <id> --path /healthz --port 3000
```

</TabItem>
</Tabs>

## Quotas

An organization can set resource caps, and each member can have an allowance inside those caps. The limit for a new app is the smaller of the amount left in your allowance and the amount left in the organization's cap. To set caps and allowances, refer to [Set quotas](/teams/quotas/).
